# 证书监控部署与排查经验

本文档记录后台“证书状态”卡片从本地验证到服务器部署的经验，适用于后续更新证书、排查证书状态异常和复盘 Docker 挂载问题。

## 1. 功能边界

证书状态功能只读取服务器本地证书文件，不做线上 HTTPS 握手校验。

当前固定监控两张证书：

| 证书 | 域名 | 当前容器内路径 |
| --- | --- | --- |
| 主站 HTTPS 证书 | `symluxlib.com` | `/etc/letsencrypt/live/symluxlib.com/fullchain.pem` |
| 静态域名证书 | `static.symluxlib.com` | `/opt/sym/certs/static.symluxlib.com/fullchain.pem` |

状态规则：

| 状态 | 含义 |
| --- | --- |
| `valid` | 证书存在、可解析、未过期，且剩余天数大于预警阈值 |
| `warning` | 证书存在、可解析、未过期，但剩余天数小于等于预警阈值 |
| `expired` | 证书存在、可解析，但已经过期 |
| `error` | 证书路径未配置、文件不存在、内容无法解析或缺少过期时间 |

默认预警阈值为 `CERT_MONITOR_WARNING_DAYS=30`。工作台右上角 tag 会根据后端返回的 `status` 变色：

- `valid` 显示绿色“正常”
- `warning` 显示黄色“即将过期”
- `expired` 显示红色“已过期”
- `error` 显示红色“检查失败”

状态不会在前端实时倒计时变化，只有定时任务刷新或点击“刷新数据”后才会重新计算。

## 2. 服务器目录规范

主站证书由项目内 `certbot` 目录维护，并挂载到容器内的标准 Let's Encrypt 路径：

```text
/root/project/sym/certbot/conf/live/symluxlib.com/fullchain.pem
-> /etc/letsencrypt/live/symluxlib.com/fullchain.pem
```

静态域名证书统一放到项目目录下，避免散落在 `/root/certs` 等临时位置：

```text
/root/project/sym/certs/static.symluxlib.com/fullchain.pem
/root/project/sym/certs/static.symluxlib.com/privkey.pem
```

容器内读取路径为：

```text
/opt/sym/certs/static.symluxlib.com/fullchain.pem
```

`certs/` 必须加入 `.gitignore`，证书和私钥不能提交到 Git。

```bash
grep -n '^certs/' .gitignore || echo 'certs/' >> .gitignore
```

## 3. 环境变量

生产 `.env.docker` 中配置证书监控路径：

```env
CERT_MONITOR_MAIN_CERT_PATH=/etc/letsencrypt/live/symluxlib.com/fullchain.pem
CERT_MONITOR_STATIC_CERT_PATH=/opt/sym/certs/static.symluxlib.com/fullchain.pem
```

可选配置：

```env
CERT_MONITOR_ENABLED=true
CERT_MONITOR_INTERVAL_SECONDS=21600
CERT_MONITOR_WARNING_DAYS=30
```

注意：

- `.env.docker` 是服务器环境文件，不提交 Git。
- 路径必须填写“容器内路径”，不是宿主机路径。
- 如果路径写宿主机路径但没有挂载进容器，后台会显示“证书文件不存在”。
- `api`、`worker`、`beat` 使用非 root 用户运行。证书目录需允许 UID `10001` 遍历，`fullchain.pem`
  需允许读取；不要因此放宽 `privkey.pem` 的权限。

## 4. Docker Compose 挂载

`api`、`worker`、`beat` 都需要能读取证书目录。

原因：

- 手动刷新接口在 `api` 容器内同步读取证书。
- 定时刷新任务由 `beat` 调度、`worker` 执行。
- 三个服务的文件视图必须一致，否则会出现手动刷新和定时刷新结果不一致。

在 `compose.yaml` 的 `api`、`worker`、`beat` 服务中挂载：

```yaml
volumes:
  - uploads_data:/opt/sym/uploads
  - tmp_data:/opt/sym/tmp
  - ./certbot/conf:/etc/letsencrypt:ro
  - ./certs:/opt/sym/certs:ro
```

修改后重建后端相关服务：

```bash
docker compose -f compose.yaml --env-file .env.docker up -d --build api worker beat
```

检查状态：

```bash
docker compose -f compose.yaml --env-file .env.docker ps
```

## 5. 容器内验收

先验证文件是否能被 `api` 容器看到：

```bash
docker compose -f compose.yaml --env-file .env.docker exec api ls -l /etc/letsencrypt/live/symluxlib.com/fullchain.pem
docker compose -f compose.yaml --env-file .env.docker exec api ls -l /opt/sym/certs/static.symluxlib.com/fullchain.pem
```

再验证文件内容确实是 PEM 证书：

```bash
docker compose -f compose.yaml --env-file .env.docker exec api sh -c "head -n 2 /etc/letsencrypt/live/symluxlib.com/fullchain.pem"
docker compose -f compose.yaml --env-file .env.docker exec api sh -c "head -n 2 /opt/sym/certs/static.symluxlib.com/fullchain.pem"
```

预期输出包含：

```text
-----BEGIN CERTIFICATE-----
```

如果 `ls` 报 `No such file or directory`，优先排查：

- 宿主机文件是否存在
- `compose.yaml` 是否挂载了对应目录
- `.env.docker` 是否填写了容器内路径
- 服务是否已经重建或重启

## 6. 工作台验收

进入管理后台工作台，点击“证书状态”卡片右上角“刷新数据”。

正常结果：

- 主站 HTTPS 证书显示“正常”
- 静态域名证书显示“正常”
- 到期时间有具体值
- 剩余天数有具体值
- 最后检查时间更新为本次刷新时间
- 顶部提示“当前没有需要处理的证书提醒”

如果证书不存在：

- 状态显示“检查失败”
- 到期时间显示 `-`
- 剩余天数显示“剩余天数未知”
- 错误文案显示“证书文件不存在”

如果证书文件存在但内容不是有效证书：

- 状态显示“检查失败”
- 错误文案显示“证书内容异常”

## 7. API 验收

手动刷新接口：

```bash
curl -X POST http://localhost:6868/api/v1/base/certificate-status/refresh \
  -H 'Accept: application/json' \
  -H 'token: <后台登录 token>'
```

工作台概览接口：

```bash
curl http://localhost:6868/api/v1/base/dashboard_overview \
  -H 'Accept: application/json' \
  -H 'token: <后台登录 token>'
```

响应中关注：

- `certificate_statuses`
- `certificate_warning_total`
- 每项里的 `status`
- 每项里的 `not_after`
- 每项里的 `days_remaining`
- 每项里的 `last_error`

不要把真实 token 写入文档、提交记录或聊天记录。

## 8. Celery 验收

查看 worker 是否注册证书刷新任务：

```bash
docker compose -f compose.yaml --env-file .env.docker logs --tail=80 worker
```

预期任务列表包含：

```text
certificate_monitor.refresh_statuses
```

查看 beat 是否运行：

```bash
docker compose -f compose.yaml --env-file .env.docker logs --tail=80 beat
```

手动刷新不依赖 Celery，点击按钮后应立即返回最新状态。Celery Beat 只是兜底定时刷新，默认每 6 小时执行一次。

## 9. 常见问题

### 9.1 页面刷新返回 500

优先看 API 日志：

```bash
docker compose -f compose.yaml --env-file .env.docker logs --tail=120 api
```

这次排查中的关键经验：

- “证书文件不存在”和“证书内容异常”都应该作为业务状态写入 `error`，不应该让接口返回 500。
- 如果接口返回 500，说明后端异常没有被证书监控 service 正常吸收，需要先修代码或查看堆栈。

### 9.2 页面显示“证书内容异常”

先确认容器内文件是不是实际 PEM 证书：

```bash
docker compose -f compose.yaml --env-file .env.docker exec api sh -c "head -n 2 <证书路径>"
```

如果不是 `-----BEGIN CERTIFICATE-----`，说明路径指向了错误文件，或复制了错误内容。

### 9.3 页面显示“证书文件不存在”

这通常不是前端问题，而是容器内路径不可见。

按顺序检查：

```bash
docker compose -f compose.yaml --env-file .env.docker exec api ls -l <证书路径>
grep -n '^CERT_MONITOR_.*CERT_PATH=' .env.docker
grep -n -A12 -E '^  (api|worker|beat):' compose.yaml
```

重点判断：

- `.env.docker` 写的是不是容器内路径
- `compose.yaml` 是否把宿主机目录挂进容器
- 修改 Compose 后是否重建了 `api worker beat`

### 9.4 本地 Docker 没有证书文件

这是正常开发状态。

本地没有真实证书文件时，卡片应显示：

- `status = error`
- 错误文案为“证书文件不存在”
- 不应返回 500

本地 Docker 验收重点是错误状态是否稳定，而不是证书是否真实有效。

### 9.5 `aerich upgrade` 显示没有迁移项

如果代码里新增了模型或迁移，但命令显示：

```text
No upgrade items found
```

需要区分两件事：

- 迁移记录是否已经执行过
- 数据库里目标表是否真实存在

不要只根据 `aerich upgrade` 输出判断功能可用。应结合应用启动、接口调用和数据库表结构确认。

## 10. 后续维护流程

主站证书：

1. 由 `certbot renew` 自动续期。
2. 续期后 reload Nginx。
3. 到工作台点击“刷新数据”。
4. 确认到期时间和剩余天数已经更新。

静态域名证书：

1. 按 `docs/QINIU-STATIC-CERT-RENEWAL.md` 续签并上传七牛。
2. 将导出的 `fullchain.pem` 和 `privkey.pem` 同步到 `/root/project/sym/certs/static.symluxlib.com/`。
3. 到工作台点击“刷新数据”。
4. 确认到期时间和剩余天数已经更新。

静态域名当前不是全自动续期。后续如果要规范化，应优先补齐静态证书续期和同步流程，而不是只依赖页面提醒。

## 11. Git 注意事项

可以提交：

- 代码实现
- 迁移文件
- 文档
- `.gitignore` 中的 `certs/`
- `compose.yaml` 中的只读证书目录挂载

不能提交：

- `.env`
- `.env.docker`
- `certs/` 目录内容
- 私钥 `privkey.pem`
- 真实 token、数据库密码、对象存储密钥

服务器上如果存在本地化 Nginx bootstrap 配置，提交前要单独确认是否属于项目通用规范，避免把仅适用于当前服务器的临时配置写入主分支。
